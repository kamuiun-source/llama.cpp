# 異種GPU MoE推論エンジン 実装計画

対象はWindows 11、RTX 4070 Ti CUDA、MI50 Vulkan、Flash-Next `UD-IQ3_XXS`。初回の実機条件と最終構成は [基本設計書](basic-design.md) を参照する。

作業は原則として、設定で確認できる範囲を先に確定し、製品コードの変更を一つの責務に絞ってレビューする。各Issueに依存関係、変更候補、受入項目と確認方法を残す。下表のファイルは変更候補で、実機結果に合わせて差分を絞る。

## Phase 0〜2の着手順

| Issue | 対象と依存関係 | 最小の受入確認 |
| --- | --- | --- |
| **0A GPU認識** | 同一ビルドで `--list-devices` を実行。RTX CUDAとMI50 Vulkanのデバイス名と空き容量を記録 | 同じバイナリから両デバイスを識別できる |
| **0B 分割ロード** | 0Aの後。既存CLIでFlash-Nextを2K、MTPオフ、PLE遅延読み込みで起動 | 固定した短文を1回生成し、ロードと生成、配置、PLEの遅延読み込み、VRAM・RAMを同じ実行で確認 |
| **0C 35Bでの切り分け** | 0Bで容量や演算互換性が障害になった場合。動作確認済みの35Bと既存設定を使う | 同一ビルド・両デバイスでの35Bの起動結果から、問題がFlash-Next固有か切り分ける |
| **0D MTPの基準値** | 0Bの後、RTXの空きVRAMがあれば既存MTPを追加 | 0Bと同じ本体設定でDecode速度、確定トークン数、RTXのVRAMを比較 |
| **1A 固定配置の確認** | 0Bの設定、または0Cの35Bで、配置ログから演算先を確認 | 1回の短文生成でAttention・RouterはRTX、対象のRouted ExpertはMI50で実行されたかを記録 |
| **1B 必要な演算だけ固定** | 1Aで配置のずれが出た場合。`src/models/qwen4exp.cpp`、`src/llama-context.cpp`、`src/llama-graph.cpp` の関連箇所を候補にする | 1Aと同じ入力で演算先の修正と出力の妥当性を確認 |
| **2A 転送と待ち時間の計測** | Phase 1の後。既存ログを優先し、不足する場合は `ggml/src/ggml-backend.cpp` 等の必要な境界に計測を追加 | 同一モデルでPrefillとDecodeを1条件ずつ取得し、Activation転送量・待ち・演算時間を識別できる |
| **2B Activation転送の改善** | 2Aで主要な待ちを確認した場合。MI50での集約、転送バッファ再利用など、原因に対応する変更を一つ選ぶ | 同じ条件の変更前後で、出力の妥当性と対象の待ち時間を確認 |

Phase 2BとMTP比較は、Flash-Nextの動作確認とExpert配置の正確性を妨げない順序で進める。35Bだけで成立した場合は、固定配置を35Bで切り分けつつ、Flash-Nextへの適用は別途確認する。

## Phase 3の実装単位

| Issue | 対象と変更候補 | 最小の受入確認 |
| --- | --- | --- |
| **3A Expertの常駐先を分ける** | Phase 1の後。`src/llama-model-loader.cpp` と `src/llama-model.cpp` で層・Expert IDごとの所属と索引を持ち、重みをMI50常駐分とRAM常駐分に分ける。 | 固定配置1件で、元IDがすべて一方の常駐先から引け、gate/up/downが同じExpertを指すことと、GPU常駐分の恒久的なRAMコピーがないことを確認 |
| **3B-1 必要なExpertをMI50で計算する** | 3Aの後。`src/llama-moe-cache.cpp`、`src/llama-graph.cpp`、`src/models/qwen4exp.cpp` で、Routerの選択後に不足分だけを入れ替え枠へ転送する。まず転送完了を待ってMI50で計算し、結果をRTXへ返す。 | 常駐Expertだけを使うケースと、RAM側のExpertを含むケースで出力と実行先を確認。後者は複数ステップで枠を再利用し、コピー待ちと読み終わり後の再利用を同じ実行で確認 |
| **3B-2 転送と常駐Expertの計算を重ねる** | 2Aと3B-1の後。転送を発行し、MI50上ですぐ実行できるExpertの計算を始める。転送したExpertは完了を待って計算する。既存ggml/Vulkanの経路を使う。 | 3B-1のRAM側Expertを含むケースを再利用し、出力と転送対象を確認したうえで、転送と計算が実際に重なった時間を比較。MTPが使える場合は確定1トークンあたりの転送量も確認 |
| **3C 常駐Expertの選び方を比較する** | 3B-1の後。Routerの選択ログまたは既存トレースを使い、固定したVRAM予算で配置案を比較する。 | 1本の固定トレースで、配置ごとのRAM→MI50転送量と残る待ち時間を比較 |

3Aはロード時の配置で受け入れ、実行経路は3B-1でつなぐ。3B-1の完了時点で、常駐とRAM上のRouted ExpertをMI50で処理できる基準を確立する。3B-2はその基準と比較し、Windows Vulkanで待ちが減るかを判定する。

3Aの初期配置は、各層で公開 `hits` 上位300個をMI50に置く案を使う。手元の `UD-IQ3_XXS` では48層のRouted Expert重みが合計27.44 GiBになる。入れ替え枠と作業領域を含めて収まるかは実機で確認する。公開BF16データの推定ヒット率は固定300個で87.84%、同じ重み容量で層を横断して選択回数÷バイト数の順に充てる配置で88.18%。5件に1件のプロンプトを順位作成から外した比較でも86.78%から87.12%だった。いずれもRouterの選択回数ベースで、手元のDecodeの転送量や速度は未計測。層ごとの可変配置は3Cの改善候補とする。 [公開Expert Activation Map（集計に使用した版）](https://huggingface.co/datasets/tcclaviger/Qwen3.8-Flash-Next-expert-activation-map/tree/54779ca)

## Phase 4の実装候補

| Issue | 着手条件 | 最小の受入確認 |
| --- | --- | --- |
| **4A MI50を2枚使う** | 3B-1成立後、2枚構成を用意できたとき | 同じモデル・入力で1枚と2枚を比較し、Expert配置、RTXで合算した出力、カードごとの負荷を確認 |
| **4B 配置調整・3枚目** | 4Aで容量または負荷偏りに改善余地を確認したとき | ボトルネックが出た1条件で変更前後を比較 |
| **4C 長文・画像** | 短文の固定配置が安定した後。長文と画像入力はIssueを分ける | 各Issueで対象の1入力を使い、長文では実コンテキスト長とDecode速度、画像では入力と出力を確認 |
| **4D SSD上のExpert** | Expert重みのRAM予算を超える場合 | SSD上のExpertが選ばれる1条件で、出力とI/O待ちを確認 |

テストは [基本設計書のテスト方針](basic-design.md#テストの基本方針) に従い、各受入項目で最大4ケース。追加ケースが必要になった場合は、既存の確認で代替できるかを先に確認し、優先度の低いケースは改善候補として残す。
