# ROCm固定3幅のデコード全体の改善

`codex/rocm-single-bank-mtp3` の `ac5bb7770` を起点にする。RTX 4070 TiとMI50で、単一バンク・固定3位置、同じ8,192トークンの入力とMTP設定を使う。Expert転送隠蔽の試作を切り、各変更を個別に比較する。

| 順位 | 変更範囲 | 確認条件 |
| --- | --- | --- |
| 1. Shared Expertの並行化 | Routed ExpertのROCm側のグラフを発行した後、依存関係と上書きの安全性を確認したCUDA側Shared Expertを先に発行する。 | 固定3位置で先行発行が発動し、同じ生成結果を得る。CUDA側のShared ExpertとROCm側のRouted Expertの実行区間、および生成速度を確認する。 |
| 2. RTXとMI50間のホストステージング | 入力の一括転送と戻りの単独転送について、両ランタイムで使えるピン留め領域を比較する。Router IDのホスト参照を維持する。 | 両方向の発動、出力、転送バイト数、同期と生成速度を確認する。 |
| 3. 幅3のSSM畳み込みと履歴の融合 | CUDAの3位置向けに畳み込み・SiLUと履歴保存を融合する。巻き戻り位置から選ぶ履歴を既存経路と合わせる。 | 3位置の融合発動、候補棄却後の出力と巻き戻し、生成速度を確認する。 |

以前の同じ8K入力の再実行ではRTXとMI50の計算の重なりは0 msだった。MI50側でExpert重み以外のメモリコピーはD2Hが14.36 ms、H2Dが18.16 msで、GPU間のactivationのほか同じ方向の転送も含む。RTXの通常SSM畳み込みカーネルの合計は2.91 msで、履歴を作るコピーは別に実行される。MTPのpending行のホスト処理は計算と重ならなかった時間が1.91 msだった。これらの範囲の差を考慮して、GPU同士の並行化と受け渡しを先に試す。

## Shared Expertの先行発行

`GGML_SCHED_HIP_SHARED_OVERLAP=1`。固定3位置で、ROCm側のRouted Expertの出力を待たずにCUDA側Shared Expertの独立した部分を発行する。既存の依存関係、コピー先へのエイリアス、バッファ所有者の確認を通過した場合に使う。合流は従来のホスト経由の戻り転送を待つ。

OFF、ON、ON、OFFの順で、各試行の8K初回とキャッシュ再実行を取得。全8応答で128トークンのIDと生成テキストが一致し、MTPは各応答100提案中76採用。ONは各試行で4,500回のShared Expert先行発行を記録した。実行した3位置検証100回に対して1回あたり45層。

| --- | ---: | ---: |
| 8K初回の生成速度（tok/s、合算） | 33.01 | 33.87 |
| キャッシュ再実行の生成速度（tok/s、合算） | 41.66 | 42.64 |
| 初回のExpert転送完了待ち（ms / 応答、平均） | 399.43 | 410.36 |
| 再実行のExpert転送完了待ち（ms / 応答、平均） | 161.23 | 166.01 |

生成速度は初回+2.62%、再実行+2.36%。Expert重みの転送量は全試行一致した。生ログと集計は Git 外の `/tmp/llama-rocm-mtp3-decode-pipeline/shared-overlap/`。

別のキャッシュ再実行でNsight Systemsとrocprofv3を時刻合わせした。以前のOFFトレースではRTXとMI50の計算の重なりが0 ms、今回のONは64.64 ms。ONではスケジューラログにもROCmのRouted Expert直後のCUDA Shared Expert発行がある。Expert重みのH2DはONでも248.96 msがGPU計算と重ならず、主な効果は両GPUの計算の重複だった。プロファイル付きの128トークン生成とトレース書き出しは完了した。終了処理で残ったプロファイル用コンテナは停止した（終了コード143）。この実行の時間は通常の速度集計に含めていない。

## CUDAとROCmの両方で登録するホスト領域

`GGML_SCHED_HIP_DUAL_PINNED_HANDOFF=1`。固定3位置の受け渡しで、スケジューラごとに128 KiBの領域をCUDAとROCm双方の書き込み可能なホストメモリとして登録する。両方の登録が通った場合に限り、入力一括転送と反対向きの単独転送で使う。解放前に両方の登録を解除する。Router IDをホスト側で参照する処理を維持する。

比較ではShared Expert先行発行をOFFにし、`GGML_SCHED_HIP_BATCH_DEVICE_INPUTS=1` と `GGML_SCHED_HIP_HANDOFF_TIMING=1` を両条件に設定する。方向別に転送件数、バイト数、ホスト経由で読み書きする時間を比べる。読み書き時間は前段にある明示的なGPU同期待ちを含まない。

以降の実機計測は、ユーザーの指示でONだけを実行し、モデル・8K入力・設定が同じ既存のOFF試行を参照する。

### 同条件のGPUトレースでの照合

別の② ONで、キャッシュ再実行だけをNsight Systemsとrocprofv3で記録した。ホストの受け渡し時刻をNVTXとROCTxで両GPUのタイムラインに合わせた。50検証の各方向2,400件が通常実行の集計と一致し、生成ID・テキストとMTP採用数も同じだった。1検証は通常52.14 ms、トレース時60.14 ms。生成速度は42.32 tok/sと36.59 tok/sだった。以下はトレース内で照合した数値で、通常時の削減見込みには換算しない。

| 転送元待ち（ms / 検証） | CUDA→ROCm | ROCm→CUDA | 合計 |
| --- | ---: | ---: | ---: |
| ホストの待ち | 15.36 | 16.82 | 32.18 |
| 転送元の計算カーネルと重複 | 14.89 | 16.10 | 30.99 |
| 転送元で計算・コピーの活動を観測しなかった時間 | 0.39 | 0.72 | 1.11 |

転送元待ちの96.5%で同じGPUの計算またはコピーが動いていた。転送先待ちはトレースでも合計0.23 ms/検証だった。両方向の読み書きはホスト計7.61 ms/検証で、この中の同期API区間のうち対象GPUの活動が観測されなかった時間は4.92 ms/検証。そのうち4.51 msがMI50側の書き込み・読み出しに集中した。転送元・転送先待ちも含めた同じ集計は6.06 ms/検証で、実行中にGPUの活動が記録されなかった区間を示す。ドライバだけの時間や、同期方式変更で回収できる時間はここから特定できない。

次の転送改善は、小さいテンソルのMI50側受け渡しに絞り、入力3本のH2Dと戻りのD2Hで発行から完了までの待ちを減らせるか調べる。両区間はプロファイラーなしでも合計5.29 ms/検証で、読み書き6.24 msの約85%を占めた。ExpertのステージングCPUコピーは2.27 ms/検証。4 msの着手基準を下回り、原本全量を固定した直接DMAの既存試作では再実行が41.46から37.11 tok/sに低下した。MMVQは別の施策として、同一Expertを選んだ3行で重み読み出しと復号が実際に共有されるかを確認する。

非同期化では、既存のバックエンド非同期APIを候補にする。入力H2Dと戻りD2Hで同じピン留め領域を再利用する場合は、上書き前に前のDMA完了を保証する。MI50の計算ストリームにD2Hを連結する場合は、同じ依存に対するMI50の待ちを1回にまとめ、RTXから読み始める前にD2Hを完了させる。発行と待ちを合わせた本体検証時間で判断する。スロット表はコールバックのローカル配列から転送するため、別途ステージングの寿命を確保する。昇格停止を比較する場合は、動的常駐を切ると単一バンクの固定3幅の条件も変わるため、昇格判定だけを止める。書き戻しを遅延させる場合は、完了まで退避元のGPU枠と原本のRAM枠を保護する。

通常実行のサーバーは終了コード0。トレースでは応答と両プロファイラーの出力保存を確認後、終了待ちのコンテナを停止したため終了コード143だった。再エクスポートしたSQLiteの整合性検査はOK。通常集計とトレース照合結果は Git 外の `/tmp/llama-rocm-mtp3-decode-pipeline/pinned-handoff-breakdown/`。

#### 入力H2Dの試作結果

## Expert原本の連続配置と直接DMAの調査

単一バンクの現行レイアウトは、RAMとVRAMともに各層のdown、gate、upごとに別の量子化テンソルを持つ。RAMは各プレーン212 Expert、MI50は各プレーン300常駐＋30仮置き。各Expertのアドレスは `plane_base + slot * plane.nb[2]`。昇格後は退避した物理スロットを仮置きに回すので、論理的に近いExpertや仮置き枠が物理的にも連続する保証はない。現行のステージングは選ばれたExpertの3面を連続に詰めた後、宛先が異なるため3本のH2Dを同一ストリームへ発行して最後に1回待つ。既存の原本直接転送フラグはステージングのCPUコピーを省くが、3本の発行を維持する。

### 連続コピーにできる範囲

| 配置 | H2DまたはD2Hの発行数と制約 |
| --- | --- |
| 現行の3面、またはRAM側だけExpert単位 | 1 Expertあたり3本。RAMをピン留めすればCPUステージングコピーは省ける。現行の3面は等幅・等ピッチの矩形ではなく、1回の `hipMemcpy2DAsync` で表せない。 |
| RAMとMI50を同じExpert単位に配置 | 1 Expertあたり連続コピー1本。別Expertも、RAMとMI50で同じ順に連続するときに限り1本に結合できる。 |
| MI50の既存プレーン配置を維持して着地用バッファを追加 | PCIe上は1 Expertあたり1本にできるが、MI50内部のscatterで既存の3面へ移す必要がある。同期点と追加メモリトラフィックを含めて比較する。 |

既存8Kキャッシュ再実行のRouter記録では、50検証で1,586 Expert・3,244,083,200 Bをアップロードした。平均1.95 MiB/Expert、61.88 MiB/検証。現行の4,758本を共通配置では1,586本にできる。GPU側の書き込み先だけで連続区間を数えても1,579区間で、プレーンごとの結合では最大21本しか減らない。直接転送で複数Expertをまとめるには、RAMスロットの連続性も必要。

同じ物理スロット内に3面を並べ、各面を独立した量子化テンソルとして同じバッファの異なるオフセットから参照することは、ggmlのバイトストライド表現で可能。MMVQとMMQは `nb[2] / ggml_type_size(type)` をExpertストライドとして渡すため、`nb[2]` は各面の量子化ブロックのバイト数で割り切れる共通値にする。単なる3面サイズの合計を使うと一部の層で切り捨てが起きる。128 B境界も維持する案では、現モデル48層でRAM 167 MiB、MI50 260 MiBの追加パディングと見積もった。実測のVRAM残1,130 MiBを基に収まる可能性はあるが、配置変更後の実機容量は未確認。

最小の設計変更は、生のExpertスロット配列を管理する領域と各プレーンの量子化テンソルの参照を分けること。ローダーはGGUFのプレーン順に読んで、宛先のExpertスロットと面オフセットへ分配する。プレーンの実データ長は別項目に持たせる。現行のロード、compact prefill、退避、書き戻しは `nb[2]` をプレーンの転送バイト数にも使うため、共通ストライドを指定するだけでは隣の面までコピーする。ゼロ初期化と量子化末尾のパディングも共通バッファの所有者が管理し、decode・prefill双方のバックエンド経路で出力を確認する。

### ピン留めと直接書き戻し

ROCm 7.2.1の同じDockerイメージ、通常UID、memlock上限8 MiBで小規模な確認を実施した。匿名mmapの2 MiB・512 MiBと、posix_memalignの64 MiBが `hipHostRegister(..., hipHostRegisterPortable)` に成功し、両端の2 MiBでH2DとD2Hの往復が一致した。比較用の `hipHostMalloc` 64 MiBも成功。過去の実モデルではネイティブの `hipHostMalloc` で20,824,166,400 B（19.39 GiB）を2回確保できた。21 GiB級の `hipHostRegister` は未試行。8 MiBのmemlock値だけで可否は判断しない。前回の全量ピン留めによる直接DMAではCPUコピーがなくなったが、再実行の速度は落ち、完了待ちにばらつきがあった。

直接D2Hで昇格元のRAM枠を再利用するには、その枠を読むH2Dが完了していることを保証する。現在の非同期昇格は退避データを別のピン留め領域に受け、完了後のコピーと所有権更新で整合性を保つ。原本へ直接書く場合も、全データの完了後に所有権を更新する。途中失敗まで吸収するなら、連続のピン留め予備1枠に受けて確定時に枠を交換する方式を候補にする。同期済みの従来配置でも3本の直接D2Hは可能で、双方を共通配置にしたときは1本に減らせる。

全ONのキャッシュ再実行でExpertアップロードのステージングCPUコピーは2.08 ms/検証、H2D発行後の完了待ちは3.76 ms/検証。完了待ちにはストリームの待ちが含まれるので、純粋なDMA時間や削減量として扱わない。共通配置で発行回数は減っても総バイト数はほぼ同じ。設計検証の順序は、実際の量子化と共通ストライドを使う小規模なロード・H2D・推論・D2Hの照合、その後に実モデルで転送量・API発行数・完了待ち・生成速度を確認する。

ピン留め確認、配置長と連続区間の集計はGit外の `/tmp/llama-rocm-expert-tuple-dma-study/`。
