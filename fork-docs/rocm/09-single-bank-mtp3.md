# ROCm 単一バンクの固定3幅 MTP

統合ブランチ `d9287e566` から `codex/rocm-single-bank-mtp3` に分ける。RTX 4070 Ti と MI50 で、Flash Next UD-IQ3_XXS と Q8_0 の MTP ドラフトを使う。

| 作業 | 変更範囲 | 確認条件 |
| --- | --- | --- |
| 単一バンクの検証幅を拡張する | 単一バンクの動的配置で固定3位置を許可し、最大30 Expert 選択を既存の仮置き枠とアップロード処理で扱う。 | 3位置が1回の本体検証に入り、2幅と既存の分割バンクの設定が使える。 |
| 候補棄却時の巻き戻しを確認する | 本体の再帰状態スナップショットとドラフトの部分削除を使う。 | 両候補棄却、第1候補のみ採用、両候補採用で、それぞれ本体とドラフトの末尾が2、1、0位置戻り、次の検証に進む。 |
| 同じ8K入力で2幅と3幅を比較する | 配置プロファイル、コンテキスト、入力、生成上限をそろえる。同じバイナリで固定幅を切り替える。 | 生成速度、第1・第2候補の採用率、GPU同期待ちを含む本体検証1回の時間を記録する。巻き戻しの詳細ログは別の実行で採る。 |

単一バンクの `LLAMA_EXPERT_HIP_DYNAMIC_RESIDENCY=1` 設定に、固定3幅では `LLAMA_MTP_VERIFY_THREE=1` と `--spec-draft-n-max 2` を加える。通常の `-ub 2` は維持する。仮置きは20枠から30枠へ広がり、広幅Prefillの転送に使うのは従来と同じ10枠ずつの2組。候補1個の固定2幅では `--spec-draft-n-max 1` を使う。

固定3幅の検証グラフは、3トークンの通常Prefillとは区別して再利用する。HIP の生成検証では packed decode で Router ID とスロット表を処理する。初期試作では幅だけを判定したため生成検証が compact prefill に入り、その速度は採用比較から除いた。

## 実測

同じバイナリと8,192トークンの入力、コンテキスト容量34,816、greedy、128トークン生成。単一バンクの動的常駐とピン留めアップロード、`LLAMA_EXPERT_HIP_PREFILL=serial` を共通とした。順序は2幅、3幅、3幅、2幅。初回入力はすべてキャッシュなしで評価し、生成速度にはPrefillを含めない。GPU同期待ちを含む本体の検証時間を集計した。

| 検証幅 | 生成（各試行と合算） | 検証回数 / 試行 | 検証平均 | 第1候補 / 試行 | 第2候補 / 試行 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2幅 | 28.61 / 28.34、合算28.47 tok/s | 69 | 59.35 ms | 57 / 69 | — |
| 3幅 | 32.39 / 33.46、合算32.91 tok/s | 50 | 69.12 ms | 42 / 50 | 34 / 50 |

合算は最初のトークン後の127トークン/試行を用いた。3幅は+15.6%。同じ入力をキャッシュから再実行した補足値は2幅37.91、3幅41.25 tok/s。初回の生成トークン列は幅間で21トークン目から分かれた。MI50のモデルバッファは29,976から30,913 MiBに増えた。3幅の起動で `n_rs_seq=2`、Prefill最大512、生成時の3位置のpacked decodeで Router ID のホストコピー再利用を確認した。

## 巻き戻し

固定3幅の診断を、同じ8K入力の初回とキャッシュ再実行で行った。各試行で50回の3位置・3出力検証を記録した。両候補棄却8回では、本体とドラフトの末尾がともに2位置戻った。第1候補だけ採用した8回は1位置、両候補採用34回は0位置だった。両試行を通じて復元位置の不一致とチェックポイント再実行は0件。次の3位置検証の先頭は、試行末尾を除く98件すべてで復元位置の直後だった。両試行は入力8,192、出力128、切り詰めなし、診断コンテナ終了コード0。

同じ診断のRTXトレースでは、8Kの3位置検証で密なQSA Flash Attentionを600回（50検証 × 12層）確認した。計測と診断の生ログは Git 外の `/tmp/llama-rocm-single-bank-mtp3/`。

## RAM原本からMI50へ直接アップロードする試作

| 作業 | 変更範囲 | 確認条件 |
| --- | --- | --- |
| ExpertのRAM原本をHIPから転送できるようにする | モデルが保持するRAM側のExpert原本をHIPのピン留めメモリにする。原本の恒常的な複製を増やさず、書き戻し先も同じRAM枠とする。 | 直接転送の指定時にピン留めと転送の適用を確認できる。既定は従来の経路を使う。 |
| 生成中のステージングコピーを省く | 単一バンク・固定3幅・並行化OFFの生成中に、各プレーンをRAM原本から仮置き枠へ転送する。転送完了後に既存のスロット割り当てを公開する。 | 同じモデルと8K入力で、生成ID、MTP採用、転送件数と量を照合する。従来版と生成速度、CPUでのステージングコピー時間、転送完了待ちを比較する。 |

`LLAMA_EXPERT_HIP_MTP3_DIRECT_RAM=1` で有効化する。既存のHIPホストバッファ型で全RAM原本を確保し、テンソルごとに実際のバッファ型を確認する。ページ可能メモリに置かれた原本があれば、バイト数を記録して起動を止める。3位置検証のミス時に従来と同じMI50ストリームへ原本の各プレーンから非同期H2Dを発行し、既存の同期を通ってから昇格・書き戻しとスロット更新に進む。通常の1・2位置デコードとPrefillでは既存のステージング経路を使う。

`LLAMA_EXPERT_PROFILE_RAM_COPY=1` の `target_verify` を集計する。`cpu_ms` はCPUによるステージングへのコピー時間、`upload_wait_ms` は全プレーンの転送発行後に既存のストリーム同期で待った時間、`direct_bytes` は原本から直接転送した容量。発行中に進行したDMAの時間は同期での待ちに含まれない。

同一ビルド・同一8,192トークン入力でOFF、ON、ON、OFFの順に実行。各サーバーで128トークンを2回生成し、2回目の入力では8,188トークンを再利用した。全8応答で生成IDとテキストが一致し、各応答で3位置検証50回、候補100件中76件採用だった。3位置検証のアップロード量は初回8,783,385,600 B、再実行3,244,083,200 Bで全試行一致。ONの両起動で原本20,824,166,400 Bを全量ピン留めし、3位置検証では転送の全量が原本からの直接DMAになった。

| 指標 | 8K初回 OFF | 8K初回 ON | キャッシュ再実行 OFF | キャッシュ再実行 ON |
| --- | ---: | ---: | ---: | ---: |
| 生成速度の合算（tok/s） | 33.51 | 33.23 | 41.46 | 37.11 |
| 生成速度の各試行（tok/s） | 33.53 / 33.50 | 33.96 / 32.54 | 41.50 / 41.41 | 42.60 / 32.88 |
| ステージングコピー（ms / 応答、平均） | 318.02 | 0.00 | 119.19 | 0.00 |
| 転送完了待ち（ms / 応答、平均） | 406.32 | 691.44 | 164.34 | 636.84 |

速度は最初のトークンに続く127トークン / 応答で計算。転送時間は各応答の3位置検証50回分を合計した。再実行のONで転送完了待ちは252.36 msと1,021.32 msに分かれ、転送量と生成結果は一致。ばらつきの原因は未特定。初回の速度差は−0.83%、再実行は−10.47%。直接DMAによる安定した速度向上が確認できなかったため、既定はOFFを維持する。全コンテナの終了コードは0。生ログ、実行コマンド、集計は Git 外の `/tmp/llama-rocm-single-bank-mtp3-direct-dma/`。

## gate/upだけを分割するExpert転送の試作

| 作業 | 変更範囲 | 確認条件 |
| --- | --- | --- |
| ミス時のgate/up投影とアップロードを重ねる | 単一バンクの固定3位置検証で、Routerが選んだ常駐・仮置きヒットのgate/upを先に実行する。転送完了後はミス分だけ計算して元のレーン順へ戻す。ミス0ではgate/upを全レーン一度だけ実行する。 | 同じ層のアップロードと常駐gate/upが重なる。転送対象スロットの読み出しは完了後に行う。ミス0でミス側の投影が起動しない。 |
| SwiGLUとdownを全レーン一度で実行する | gate/upの全結果を合流し、SwiGLUとdownを既存のレーン順で各1回実行する。直接DMAはOFFで比較する。 | 同じ8K入力の生成IDとMTP採用、生成速度、Expertアップロードの完了待ちを並行化OFFと照合する。 |

`LLAMA_EXPERT_HIP_MTP3_GATE_UP_OVERLAP=1` で有効化する。転送と常駐側のgate/upを別ストリームで進め、キャッシュで選んだ仮置き枠は転送完了後にミス側のgate/upから読む。投影結果は元のレーンの位置に書き、合流後のSwiGLUとdownは各1回実行する。全ヒットの層ではミス側の投影と2つの合流演算を省き、gateとupを各1回、全レーンで実行する。スロット表の参照は残る。この試作では従来のgate/upとSwiGLUの融合を外す。

転送待ちは `LLAMA_EXPERT_PROFILE_RAM_COPY=1` の `target_verify` の `upload_wait_ms`。並行化OFFでは従来の転送ストリームを同期した時間、試作では常駐側gate/upの後で転送専用ストリームを同期した時間を集計する。どちらもホストから観測した完了待ちで、PCIe上の転送所要時間とは測定範囲が異なる。

単一バンク・固定3幅・直接DMA OFF、同じビルドと8,192トークン入力でOFF、ON、ON、OFFの順に実行。各サーバーで初回とキャッシュ再実行の128トークンずつを比較した。全8応答で生成IDとテキストが一致し、各応答で50回検証、100提案中76採用。3位置検証の転送量は初回8,783,385,600 B、再実行3,244,083,200 Bで全試行一致した。

| 指標 | 8K初回 OFF | 8K初回 ON | キャッシュ再実行 OFF | キャッシュ再実行 ON |
| --- | ---: | ---: | ---: | ---: |
| 生成速度の合算（tok/s） | 32.57 | 31.82 | 41.53 | 39.59 |
| 生成速度の各試行（tok/s） | 33.16 / 32.00 | 31.22 / 32.45 | 41.33 / 41.73 | 39.52 / 39.66 |
| 転送完了待ち（ms / 応答、平均） | 418.03 | 109.68 | 160.66 | 14.55 |
| ステージングコピー（ms / 応答、平均） | 333.67 | 318.32 | 121.25 | 119.15 |
| 3位置検証区間の合計（ms / 応答、平均） | 3,500.45 | 3,590.69 | 2,655.43 | 2,804.27 |

速度の合算は最初のトークンに続く127トークン / 応答で計算。ONの各試行では4,800層実行のうち全ヒットが2,089、ヒットとミスの混在が2,711、全ミスが0だった。転送完了待ちは初回73.8%、再実行90.9%短縮し、生成速度はそれぞれ2.3%、4.7%低下。追加の投影と合流、スロット参照、従来の融合を外した影響は個別に計測していない。この比較では既定OFFを維持する。ビルドと全コンテナの終了コードは0。生ログと再集計は Git 外の `/tmp/llama-rocm-single-bank-mtp3-gate-up-overlap/`。

## gate/upの出力バッファを共有する試作

| 作業 | 変更範囲 | 確認条件 |
| --- | --- | --- |
| hotとcoldの投影を同じgate/up出力へ書く | 単一バンクの固定3位置で、hot/coldが同じgate出力と同じup出力の重複しないレーンを埋める。SwiGLUの読み出しとcold転送の依存関係は維持する。 | 全レーンを埋め、空の側は起動を省く。対象の出力初期化と合流ADDが発行されず、SwiGLUとdownは全レーンで各1回。 |
| 同じ8K入力で従来の分割版と比較する | 両条件で同じ転送・量子化を使い、ミス0の融合と直接DMAはOFFで揃える。 | 生成ID、MTP採用、生成速度、Expert転送量と完了待ちを比較する。 |

`LLAMA_EXPERT_HIP_MTP3_GATE_UP_SHARED_OUTPUT=1` を `LLAMA_EXPERT_HIP_MTP3_GATE_UP_OVERLAP=1` と併用する。gfx906の対応するgate/up投影では、ミス側のノードがhot側の出力と同じメモリを参照する。hot/coldのマスクは補集合で、各側が元のレーン位置へ直接書き込む。空マスクの投影は発行しない。SwiGLUは両側の投影が完了してから共有出力を読む。`projection_dispatches` は実際に発行したgate・upの投影数で、Q8_1の量子化は従来どおり、発行した各投影で行う。

同一ビルドと8,192トークン入力で、分割版、共有出力版、共有出力版、分割版の順で計測した。各試行で初回とキャッシュ再実行を行い、全8応答で128生成トークンのIDとテキストが一致。各応答は3位置検証50回で、候補100件中76件採用だった。3位置検証のExpert転送量は全条件で初回8,783,385,600 B、再実行3,244,083,200 B。
