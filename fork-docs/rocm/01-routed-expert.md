# 01 Routed Expert の既存 HIP 演算

状態: 01-1〜01-4 完了。試した2位置・3位置の両ケースが、同じ MI50 の Vulkan と HIP で CPU 参照に一致した。

## 現状

CUDA と HIP が共有する `MUL_MAT_ID` に IQ3_XXS、IQ2_S の経路がある。実際に選ばれるカーネルは GPU、形状、量子型に依存する。MI50 上の Flash-Next の Expert 演算を比較できる基準を作る。

## 先行調査の結果

共有ドライブにある Flash-Next UD-IQ3_XXS の GGUF ヘッダーを確認した。表の形状は GGUF の次元順で、各層で gate と up は個別テンソル。重みの型は配布名の IQ3_XXS だけでは決まらない。

| 重み | 形状（内積長、出力幅、Expert 数） | 実際の型と層数 | 行ストライド |
| --- | --- | --- | --- |
| gate、up（各） | 2560、640、512 | IQ3_XXS 21層、IQ2_S 26層、IQ4_XS 1層 | 980、820、1360 bytes |
| down | 640、2560、512 | IQ4_NL 45層、Q2_0 3層 | 360、180 bytes |

既存の IQ3_XXS スモークケースは `type_a=iq3_xxs.*n_mats=4,n_used=4,b=0,m=16,n=10,k=256` で絞り込む。既存の512 Expertケースは IQ3_S と Q4_0 の別形状で、2位置を含まない。01-1 で既存経路を確認し、01-2 の追加が必要になった場合は、gate/up の IQ3_XXS と down の IQ4_NL を1ケースずつ作る。両ケースは2位置・10 Expert 選択を固定し、512 Expert と上位 ID が絡む挙動は別ケースとして確認する。

2026-11-20、開発用 Docker イメージの ROCm 7.2.1 で `test-backend-ops` を増分ビルドし、MI50（ROCm0、gfx906）で上記の1ケースを実行。CPU 参照との比較は `OK`、ROCm0 で 1/1 ケース合格。ソースの追加・変更は不要だった。生ログは Git 外の `/tmp/llama-rocm-01-1-smoke.log`。

01-2 は Flash-Next の代表形状を使い、2位置・10 Expert 選択を合成の16 Expert のバンクで検証した。IQ3_XXS の gate/up（入力のブロードキャストあり、M=640、K=2560）と IQ4_NL の down（スロット別入力、M=2560、K=640）は、MI50で CPU 参照との比較に 2/2 合格。生ログは Git 外の `/tmp/llama-rocm-01-2-smoke-latest.log`。512 Expert のバンク、他の量子型、モデル全体の推論はこの結果に含まれない。

01-3 は同じソースと同じ MI50 で、ROCm0（ROCm 7.2.1）と Vulkan0（RADV VEGA20）を比較した。両バックエンドで CPU 参照との比較に 2/2 合格。Vulkan → HIP → HIP → Vulkan の順で実行した。

| 2位置の演算 | Vulkan（µs/run、2回） | HIP（µs/run、2回） |
| --- | --- | --- |
| IQ3_XXS gate/up | 58.38 / 58.56 | 71.77 / 71.62 |
| IQ4_NL down | 85.92 / 85.87 | 63.88 / 63.85 |

値は固定 ID・合成16 Expert バンクを使い、繰り返し実行したグラフの同期込み時間を1演算に割ったもの。カーネルの個別プロファイルやモデル全体の生成時間は含まれない。生ログは Git 外の `/tmp/llama-rocm-01-3-perf-console-*.log`。

01-4 は2位置と同じ重み・先頭2位置の入力を保ち、3位置目の活性と固定 ID を追加した。Vulkan0 と ROCm0 ともに CPU 参照との比較に 2/2 合格。01-3 と同じ順序で測定した。

| 3位置の演算 | Vulkan（µs/run、2回） | HIP（µs/run、2回） |
| --- | --- | --- |
| IQ3_XXS gate/up | 80.59 / 80.84 | 104.79 / 104.86 |
| IQ4_NL down | 124.52 / 125.28 | 93.12 / 93.18 |

2位置・3位置とも、この形状の gate/up は Vulkan、down は HIP の方が短かった。実測は選んだ2形状の基準値として扱う。生ログは Git 外の `/tmp/llama-rocm-01-4-*-build-test.log` と `/tmp/llama-rocm-01-4-perf-console-*.log`。

## Flash-Next の QSA K 射影の切り分け

配布版の MI50 単体テストでは初回 prefill の BF16 GEMM で落ち、ROCm 6.3.3 の全体 FP32 指定で生成した。フォークでは `GGML_HIP_GFX906_QSA_K_F32=1` を指定し、gfx906 上で `blk.*.indexer.k_proj.weight` に対して BLAS が選んだ BF16 を FP32 へ切り替える。独自 Expert 配置は無効にする。

フォークの ROCm 7.2.1 開発イメージで局所指定のみを有効にし、MI50 単体の日本語生成に成功。Prompt 10.7 tok/s、Generation 7.9 tok/s。ROCm0 のモデルは 30,439 MiB、実行終了時の自己使用量は 31,205 MiB（モデル・コンテキスト・計算バッファ）。既存の全体 FP32 の 32.0 / 22.9 tok/s は ROCm 6.3.3 配布イメージのため、局所指定による速度差は判定できない。

初回ビルドは `GGML_NATIVE=OFF` に変更した後も CMake キャッシュで AVX2・FMA・F16C・AVX-512 が無効だった。Ryzen 5 7600 の対応命令を明示して CPU バックエンドを再ビルドし、同じ局所 FP32 の起動条件で Prompt / Generation を2回測定した。1回目は **31.6 / 24.7 tok/s**、2回目は **34.4 / 23.8 tok/s**。配布版 ROCm 7.2.7 の全体 FP32 は1回の測定で **34.9 / 24.2 tok/s**。フォークの同一ビルドでの全体 FP32 比較は未実施。

局所化による速度差を測る場合は、同じ最適化済みフォーク・同じ ROCm 7.2.1 で局所指定と全体 FP32 を比較する。モデル、プロンプト、生成上限、MTP 無効、コンテキストを揃える。必要なら計測と分けて rocBLAS トレースを採り、対象の形状が FP32 になったことを確認する。これまでの症状と配布版の基準値は [Linux CUDA＋HIP の引き継ぎ](../teams/linux-cuda-hip.md) を参照。
