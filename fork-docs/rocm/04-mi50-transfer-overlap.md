# 04 MI50 内の転送と演算の重複

状態: 04-1 から 04-4 まで実機確認済み。1位置混在生成と最大512位置の prefill で、MI50 の転送と Routed Expert 演算の重複を確認した。

## 現状

Vulkan 版は専用の転送処理と遅延 slot map 更新を使う。HIP では同じランタイム内の転送ストリームとイベントを使う候補がある。実機で重複できるかは測定する。

## 04-1 の調査と計測条件

- 現行の HIP 経路は RAM の各 Expert プレーンを MI50 のスクラッチスロットへ同期転送する。既存の `upload_packed` はステージングへコピーしたプレーンをまとめて投入し、完了を待つ。ここで ROCm のページ固定バッファを使えるか確認する。
- 転送を読み出す前に完了を待ち、完了後にスロット表を GPU へ公開する。転送中はステージング領域を保持する。ROCm のホストバッファ型からページ固定に失敗した場合は CPU バッファ型へ戻るため、戻り値の型を確認する。
- 比較条件は同一プロファイル・同一モデル・同一位置幅・同一入力とし、同期アップロード時間と転送量を測る。ステージングを含む時間と GPU 上の時間は別の指標として扱う。
- HIP のページ固定転送は `LLAMA_EXPERT_HIP_PINNED_UPLOAD=1` で有効。`GGML_CUDA_NO_PINNED=1` が設定されている場合は直列転送へ戻る。OFF と ON の比較では両方で `GGML_CUDA_NO_PINNED` を未設定にする。
- 開発コンテナの再ビルド時に組み込み UI の `b12371` 配布に必要なファイルが欠けていたため、CMake 設定時に `HF_UI_VERSION=b12370` を指定して復旧した。OFF と ON は同じバイナリを使う。

### 04-1 の実機結果

Flash-Next UD-IQ3_XXS を RTX 4070 Ti と MI50 に配置し、Phase 03 と同じプロファイルと入力で実行した。1位置、同期動的常駐有効、MTP 無効、`--temp 0 -n 128`。初回の試行で動的常駐も切り替わったため、その試行を除外し、条件を揃えて OFF → ON → ON → OFF を実行した。

| ページ固定ステージング | 同期アップロード区間（秒） | Generation（tok/s） |
| --- | --- | --- |
| OFF（直列転送） | 1.646 / 1.653 | 23.9 / 24.1 |
| ON（まとめて転送） | 1.265 / 1.259 | 25.0 / 25.3 |

ON では ROCm0 に26,624,000 bytesのページ固定領域を確保した。4回とも生成した回答、記録された127件のデコードトークン ID、6,255件のアップロード（12,750,822,400 bytes）、1,327件の昇格が一致した。同期アップロード区間の平均は約24%短かった。この区間はスロット選択、CPU のステージング処理、完了待ちを含む。詳細ログを有効にした1入力での計測であり、他の入力での性能は未測定。生ログは Git 外の `/tmp/llama-rocm-04-1-corrected-*.log`。

同じ2トークンを1位置ずつ処理した初層の照合では、OFF と ON の Router ID、スクラッチに読んだ down 重み、down 出力が一致した。CPU 参照との照合にも両モードで合格した。生ログは Git 外の `/tmp/llama-rocm-04-1-width-diagnostic.log`。

## 04-2 の調査単位

- 04-2a は同じ MI50 の別 HIP ストリームに、ページ固定の H2D 転送と既存の Routed Expert 演算を投入する。初層の3プレーンからなる1 Expert 分（1,971,200 bytes）と IQ4_NL down の1位置を使い、別々のデバイスバッファに配置する。`rocprofv3` の H2D とカーネルの時刻から重複区間を求め、読み戻した転送内容と演算結果を逐次実行と比較する。H2D のタイムスタンプを取得できるかも実機で確認する。 [ROCm 7.2.1 のトレース仕様](https://rocm.docs.amd.com/projects/rocprofiler-sdk/en/docs-7.2.1/how-to/using-rocprofv3.html)
- 04-2b はモデルの常駐 Expert を先に処理し、スクラッチを初めて読む演算をアップロード完了イベントで待たせる。Router による選択が確定してから投入し、前回の読み取りが終わったスロットだけ上書きする。常駐とスクラッチを一つの `MUL_MAT_ID` に渡す現在の HIP グラフでは、転送と演算を別ストリームに分けるだけでは待ちが残る。Vulkan のグラフ実装と比較して、待ちを置く位置を先に決める。

### 04-2a の実機結果

MI50 上で、ページ固定メモリからの H2D 転送（1,971,200 bytes）と、別バッファを使う1位置の IQ4_NL `MUL_MAT_ID` を、逐次実行・同時投入で各100回計測した。両条件で読み戻した転送データと GPU 出力が一致し、CPU 参照に対する正規化平均二乗誤差は `1.14e-14`。

`rocprofv3` はコンテナ内の `libdw.so.1` 不足で起動できなかったため `rocprofv2` を使った。ウォームアップを除いた H2D と演算カーネルのタイムスタンプから、逐次では交差なし、同時投入では100回すべてで交差し、平均38.0 µsの重複を確認した。GPU 上の区間は平均230.6 µsから166.9 µs。プロファイラなしのホスト計測は224.2 µsから155.3 µs。この結果の対象は独立した転送・演算の診断で、モデル内の重複は04-2bで計測する。診断コードとトレースは Git 外の `/tmp/llama-rocm-04-2a/`。

ホストの `libdw.so.1` を読み取り専用でマウントした `rocprofv3` でも再現した。逐次では交差なし、同時投入では1回あたり平均36.2 µs（H2D 時間の24.3%）の重複。生トレースは `/tmp/llama-rocm-04-2a/v3trace`。

### 04-2b の実装と検証の範囲

1位置の固定常駐から始める。既存の常駐・コールド分割グラフを使い、常駐側のスロット表を書いた後、別 HIP ストリームに不足分を投入する。スクラッチ側のスロット表を使う前に転送を待つ。中断時は予約スロットを無効化し、転送完了後にページ固定領域を再利用する。

同一モデル・入力で同期実行と比較し、生成結果、常駐とスクラッチの利用、アップロード件数を確認する。モデル実行中の H2D と MI50 カーネルの交差は、生成時間の比較と分けてトレースで確認する。

比較には `LLAMA_EXPERT_HIP_OVERLAP=serial` と `LLAMA_EXPERT_HIP_OVERLAP=1` を使う。両方で同じ常駐・コールド分割とページ固定領域、同じ転送用ストリームを使い、完了待ちを常駐演算の前に置くか後に置くかだけを変える。同期動的常駐は両条件で無効にする。

起動条件は `LLAMA_EXPERT_BATCH_TOKENS=1`、`--ubatch-size 1`、`--spec-type none`。両モードともページ固定領域を必要とするので `GGML_CUDA_NO_PINNED` は外す。実験フラグ未指定時は既存経路を使う。

Flash-Next UD-IQ3_XXS を RTX 4070 Ti と MI50 で実行し、前項と同じ入力で `--temp 0 -n 32` を指定した。`serial` → `1` → `1` → `serial` の4回とも終了コード0。生成した回答、記録された31件のデコードトークン ID、3,810件のRAMアップロードが一致した。並行側では1,960層実行で常駐演算の前に転送を投入した。

| 同じ分割グラフでの転送 | Prompt（tok/s） | Generation（tok/s） |
| --- | --- | --- |
| 直列 | 19.8 / 19.9 | 19.2 / 18.9 |
| 並行 | 23.0 / 22.8 | 22.4 / 22.3 |

転送のステージングとホスト待ちの合計は、直列が750.3 / 1,408.3 ms、並行が387.4 / 390.4 ms。直列の2回にはばらつきがあり、GPU 上の重複量は別の計測で確認する。生ログは Git 外の `/tmp/llama-rocm-04-2b-{serial1,async1,async2,serial2}.log`。

初層のトークン9419では常駐9件とコールド1件（ID 37）を照合した。両モードの実データが元 GGUF と一致し、マスク先のゼロ枠も確認した。down 出力の CPU 参照に対する正規化平均二乗誤差は常駐側 `1.11e-14`、コールド側 `1.14e-14`。直列と並行で Router ID と合算後の down 出力がバイト単位で一致した。生ログは Git 外の `/tmp/llama-rocm-04-2b-split-diagnostic.log`。

同じ入力で `-n 8` のモデル実行を `rocprofv3` で計測した。MI50 の転送専用ストリームの H2D は両条件とも6,954件（アップロードした2,318 Expert × 3プレーン）。同じ MI50 の演算ストリームの `mul_mat_vec_q` カーネルと時刻が交差した区間は、直列では0 ms、並行では合計120.1 ms。並行側の H2D 実行区間359.6 msの約33%に相当し、3,406件のコピーに交差があった。生トレースは Git 外の `/tmp/llama-rocm-04-2b/trace-serial` と `/tmp/llama-rocm-04-2b/trace-async`。

比較用に、同じ入力と1位置・固定常駐で、単一バンクのページ固定同期経路を1回計測した。Prompt 24.7 tok/s、Generation 23.8 tok/sで、分割・並行経路の Generation 22.4 / 22.3 tok/sを上回った。回答、トークン ID、3,810件のアップロードは一致した。この測定では分割経路の既定化を見送り、04-2bは明示的に有効化する。生ログは Git 外の `/tmp/llama-rocm-04-2b-static-baseline.log`。

## 04-3 の実装と検証の範囲

1位置の分割グラフに、各層1枠の昇格先を追加する。スクラッチで再利用した Expert を昇格候補とし、直近のリクエストで使っていない常駐 Expert を退避対象にする。退避する全プレーンをページ固定メモリへ読み戻し、昇格する全プレーンを未使用の常駐スロットへコピーする。

演算から見える配置は転送中に維持する。転送が完了してから、退避した重みを RAM の所有スロットへ書き戻し、所有表と次の予備スロットを更新する。中断した要求では転送を回収し、準備中の昇格先を公開しない。

通常入力で直列と並行を比較し、応答、昇格・退避件数、退避先 RAM スロットからの再読込を照合する。GPU トレースで同じ MI50 上の D2H と Expert 演算の交差を測る。

`LLAMA_EXPERT_HIP_OVERLAP_PROMOTION=1` を両条件に加え、`LLAMA_EXPERT_HIP_OVERLAP=serial` と `=1` を切り替える。同期の単一バンク用 `LLAMA_EXPERT_HIP_DYNAMIC_RESIDENCY` は外す。予備領域は各層1常駐スロット（合計98.2 MB）と、ページ固定の書き戻しバッファ1 Expert 分（最大2.66 MB）。

### 04-3 の実機結果

同じ Flash-Next と入力で `--temp 0 -n 128` を使い、直列 → 並行 → 並行 → 直列の順に実行した。4回とも終了コード0、回答と記録された127件の生成トークン ID が一致。昇格・退避は各1,407件、書き戻しは2,868,480,000 bytes、RAMからのアップロードは5,880件。退避先と同じ RAM スロットからの再読込は各262件。第5層（0始まり）の Expert 6 を RAM スロット30へ退避し、後で同じスロットから MI50 に再転送した。

分割グラフ内の生成速度は直列が21.1 / 20.9 tok/s、並行が23.1 / 23.1 tok/s。計測対象は1位置の1入力。生ログは Git 外の `/tmp/llama-rocm-04-3-{serial1,async1,async2,serial2}.log`。

`rocprofv3` の64トークン上限の診断では、両条件で892件の昇格が発生した。転送ストリームの D2H 2,676件（3プレーン × 892）が Routed Expert 演算と交差した時間は直列0 ms、並行46.4 ms（並行の D2H 実行区間137.1 msの約34%）。昇格先への同一デバイス内コピーは、同じストリームの `__amd_rocclr_copyBuffer` 2,676件として記録された。生トレースは Git 外の `/tmp/llama-rocm-04-3/trace-serial64` と `/tmp/llama-rocm-04-3/trace-async64`。

## 04-4 の実装と検証の範囲

既存の compact prefill で最大512位置の入力を処理する。同期動的常駐の単一バンクと20枠のスクラッチを使い、常駐および既存スクラッチのヒットを処理した後、未ロードの Expert を10枠ずつ二つのグループに投入する。現在のグループを演算中に別グループへ次を転送し、そのグループの演算開始前に転送完了を待つ。上書きするグループの前回の使用完了と、スロット表を登録する時点を確認する。

`LLAMA_EXPERT_HIP_PREFILL=serial` と `=1` で、両条件のグループ分けと入出力を揃える。512トークンを超える同一の通常入力を使い、処理位置幅、生成結果、転送件数、prefill 時間を比較する。別実行で転送・演算の重複も測る。

起動時は `LLAMA_EXPERT_BATCH_TOKENS=2`、`LLAMA_EXPERT_HIP_DYNAMIC_RESIDENCY=1`、`--batch-size 512 --ubatch-size 2 --spec-type none` を指定する。HIP 分割・昇格フラグと Vulkan prefill フラグを外し、ページ固定領域を使うため `GGML_CUDA_NO_PINNED` も外す。

### 04-4 の実機結果

水循環に関する644トークンの入力で `--temp 0 -n 8` を実行。直列 → 並行 → 並行 → 直列の4回とも最大512位置に到達し、生成したテキスト、トークン ID、compact 処理1,237チャンク、転送投入625回（11,289,267,200 bytes）が一致した。並行側では転送完了を待つ前に演算を投入した区間が488回あった。

| 最大512位置の prefill | 644トークンの処理時間 | Prompt（tok/s） |
| --- | --- | --- |
| 直列 | 3.701 / 3.724秒 | 174.0 / 173.0 |
| 並行 | 3.445 / 3.274秒 | 186.9 / 196.7 |

この入力では平均の prefill 時間が約9.5%短かった。入力と生ログは Git 外の `/tmp/llama-rocm-04-4/prompt.txt` と `/tmp/llama-rocm-04-4-{serial-first,async1,async2,serial2}.log`。

同じ長文を使った `rocprofv3` の2トークン生成上限の実行では、転送専用ストリームの H2D が両条件とも16,623件。MI50 の行列積カーネルとの重複は直列0 ms、並行190.3 ms（並行の H2D 実行区間874.5 msの約22%）だった。生トレースは Git 外の `/tmp/llama-rocm-04-4/trace-serial` と `/tmp/llama-rocm-04-4/trace-async`。8トークン上限の通常試行は両モードで同じ箇所まで生成した。本計測は同一入力の短い生成と長文 prefill を対象とする。
