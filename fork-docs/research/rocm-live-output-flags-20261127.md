# 固定3幅の出力比較と起動中のフラグ切り替え

`codex/rocm-integrated-test` の `c301381e5` から `codex/rocm-live-output-flags` を作成。対象は[出力の揺れを調べたときの設定](../teams/runtime-flags.md#出力の揺れを調べるon設定)。モデル読み込み時のRTX・MI50・RAMの配置、直接tuple DMAと動的常駐など、固定3幅に必要な基盤は共通とする。

[固定5問の第4問](dialogue-benchmark-prompts.md#4-コード生成)だけを、毎回新規会話にして同じサーバーへ送る。4K・生成上限512・温度0・seed 1234。各リクエスト前にスロットを消去し、会話KVとRAMプロンプトキャッシュの再利用を無効にする。Pythonコードが計算する60 ms、27 ms、55%と、日本語の説明文に書かれた値を別々に確認する。本文・生成ID・MTP採用数・処理の発動を記録する。

## 比較条件

| 試す機能 | 共通の条件と比較元 |
| --- | --- |
| CPU Expert自動配分 | 先読みOFFでCPU配分だけON。先読みONの対照でもCPU配分だけを変え、両者の併用時の影響を見る。 |
| 次層Router先読み | 固定3幅で先読みの有無を比較。配置・候補数は同じ。 |
| HIPプリフィル | 同じ配置とバッチ上限で比較し、選ばれたプリフィルの経路を確認する。 |
| MI50符号復号 | 他の対象カーネル機能をOFFにし、符号復号だけを比較。 |
| IQ2_SのQ8_1入力共有 | 符号復号ONを共通にして比較。IQ2_SのLDS先読み・4行はOFF。 |
| IQ3_XXSのLDS先読み・4行 | 符号復号を有効にして先読みだけを比較。4行は先読みON・2行を対照にする。 |
| IQ4_NL downの復号短縮 | 固定3幅で復号短縮だけを比較。 |
| catch-up＋第1候補の統合 | 固定3幅・2候補で既存のモードファイルを使う。 |
| RTXのHC down Split-K、GDN、concat、unary | それぞれ1つずつONにし、全OFFを対照にする。 |
| IQ2_S・IQ3_XXS Strata | 既存のモードファイルで型別に切り替える。IQ2_Sは符号復号とQ8_1入力共有をONにして比較する。 |
| Router予測IDの読み戻し | 次層先読みをONにしたまま読み戻しだけを切り替える。 |

最初の全OFFと最後の全OFFを照合する。会話KVは消去するが、MI50の常駐Expertはサーバー内で入れ替わる。比較結果では、設定差に加えて実行順とExpertの状態の影響も考慮する。

## 起動中に切り替える設定

- `LLAMA_GPU_OUTPUT_MODE_FILE` はGPUカーネルの既存の環境変数名をキーとし、1行に1つ `名前=on` または `名前=off` を書く。未記載の項目は起動時の設定に従う。
- `LLAMA_EXPERT_OUTPUT_MODE_FILE` には `NEXT_ROUTER_PREFETCH=on/off` と `HIP_PREFILL=on/off` を書く。必要な作業領域を起動時に確保するため、Docker起動時にファイルのパスを指定する。
- CPU Expert、catch-up＋第1候補、IQ2_S・IQ3_XXS Strata、次層Router ID読み戻しは[既存のモードファイル](../teams/runtime-flags.md#linux-rocm固定3幅の採用設定)で切り替える。

Dockerには個別ファイルの代わりにモードファイルを置くディレクトリをマウントする。待機中にファイルを同じディレクトリ内の一時ファイルから置き換え、次のリクエストで反映する。今回追加したモードを切り替えると、以前の設定で計算したプロンプトを再利用しないよう、対象・ドラフトのKVとサーバーのプロンプトキャッシュを消去する。モデルの配置と重みはそのまま使う。

### GPUモードファイルのキー

| 対象 | キー |
| --- | --- |
| MI50の符号復号・Q8_1共有・down復号 | `GGML_HIP_GFX906_IQ_SIGN_DECODE`、`GGML_HIP_GFX906_IQ2_S_PAIRED_DOT`、`GGML_HIP_GFX906_IQ4_NL_DOWN_COMPACT_DECODE` |
| IQ3_XXSのLDSと行数 | `GGML_HIP_GFX906_IQ3_XXS_LDS_PREFETCH`、`GGML_HIP_GFX906_IQ3_XXS_LDS_ROW_GROUPS` |
| IQ2_SのLDSと行数 | `GGML_HIP_GFX906_IQ2_S_LDS_PREFETCH`、`GGML_HIP_GFX906_IQ2_S_LDS_ROW_GROUPS`、`GGML_HIP_GFX906_IQ2_S_NO_LDS_ROW_GROUPS` |
| RTXのHC down・GDN | `GGML_CUDA_HC_DOWN_SPLIT_K`、`GGML_CUDA_GDN_GATED_NORM` |
| CUDA/HIP共通 | `GGML_CUDA_CONCAT_SMALL`、`GGML_CUDA_UNARY_MUL_BCAST` |

行数を選ぶキーは `off` で2行、`on` で4行。IQ3_XXSのLDSと行数のキーは従来のカーネルに適用される。IQ3_XXS Strataを使う場合はそちらの専用カーネルが優先される。

既存のDocker起動コマンドにモード用ディレクトリを追加し、その中の2ファイルを起動時に指定する。例ではホスト側の `$modes` に `gpu.conf` と `expert.conf` を置く。

```bash
--mount "type=bind,src=$modes,dst=/runtime-modes,readonly" \
-e LLAMA_GPU_OUTPUT_MODE_FILE=/runtime-modes/gpu.conf \
-e LLAMA_EXPERT_OUTPUT_MODE_FILE=/runtime-modes/expert.conf
```

たとえば符号復号だけを明示的にOFFにするには、ホスト側で次を実行してから、新規リクエストを送る。この例から省いたキーは起動時設定に戻る。

```bash
printf '%s\n' 'GGML_HIP_GFX906_IQ_SIGN_DECODE=off' > "$modes/gpu.conf.tmp"
mv "$modes/gpu.conf.tmp" "$modes/gpu.conf"
```

#### 整数除算の小数部を保持する試作

### 公開実装と論文から見た数値差の縮め方

1. **同じExpert入力に同じ量子化・丸めを使う。** vLLMのDeepSeek-V4-Flashの検証では、異なるExpert入力配置に同じ量子化規則、行ごとに同じ累積、SwiGLU積の後に一度だけ丸める処理を適用した。このフォークでは狭幅Q8_1のスケール格納がFP16、広幅MMQのIQ2_S・IQ3_XXS向けD4がFP32で、量子値の計算式も狭幅は除算、広幅は逆数乗算。まず実モデルから同じ活性・Expert ID・重みを採り、量子化されたint8とスケールの差、gate/up出力の差を別々に測る。差が確認できれば、IQ型を限定して共通の量子化を試し、整数内積の小数部保持の有無も別々に評価する。[vLLMのExpert GEMM検証](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-10-14-train-inference-consistency.md#44-expert-gemm-two-layouts-same-row-result) · [狭幅の量子化](../../ggml/src/ggml-cuda/quantize.cuh#L14) · [広幅の量子化](../../ggml/src/ggml-cuda/quantize.cu#L488)
2. **並列化の形状と加算順を切り離す。** Thinking Machines Labの公開カーネルやSGLangでは、バッチやプリフィル分割が変わっても演算の分割境界を固定する。Detentは数値を変える選択だけを固定する。今回なら同じK分割とFP32の加算順でExpert出力を作り、トークン方向の並列度を変えられるかを調べる。GGUF系のAxonは公開資料で、整数ブロック内積とFP32加算順を共通にするCUDA実装を記録している。CPU Expertにも展開する場合は入力Q8形式とExpert出力の合流順まで揃える必要がある。[Thinking Machines Labの実装](https://github.com/thinking-machines-lab/batch_invariant_ops) · [SGLangの実装解説](https://www.lmsys.org/blog/2025-09-22-sglang-deterministic/) · [Detent](https://arxiv.org/abs/2611.10611) · [Axonの設計メモ](https://github.com/HaseebKhalid1507/Axon/blob/main/docs/research/research-determinism.md)
3. **高精度の参照計算を使って最初の差を探す。** LayerCastは低精度で保持した重みをFP32演算に使い、推論のばらつきを抑えた。このフォークでは全層の演算を差し替える前に、少数のExpert行のFP32参照と、RTX側のSSM畳み込み出力、Router順位を比較する。Expertに渡る時点ですでに入力が異なる場合は、同じ活性を与えたExpert単体の結果と、モデル全体のlogitを分けて判断する。[LayerCastの論文](https://proceedings.neurips.cc/paper_files/paper/2025/hash/f80094a824ba5912d4a2de169c404a40-Abstract-Conference.html) · [公開コード](https://github.com/nanomaoli/llm_reproducibility)

推論経路間のlogit差を減らす実験と、説明に書かれる計算結果の正確さの評価は別々に行う。今回は同じ「5」が複数の経路で1位になっており、logitの再現性から計算結果の正しさは推定できない。

### 固定5問でのD4速度比較

固定3幅、4K、生成上限512、会話内のKV再利用あり。CPU Expert、Strata、次層先読みなどは採用設定を使う。整数内積の小数部保持は両条件OFF。D4は狭幅プリフィルでのみ適用されるため、実際に経路を通る狭幅の比較と、通常の広幅設定での適用確認を分ける。同じサーバーを使い、各会話の準備を揃え、生成速度、プリフィル速度、MTP採用数、回答、スワップを比較する。

狭幅では `HIP_PREFILL=off` を共通にし、同じビルド `99509337e`、同じサーバーでD4 OFF → ON → ON → OFFの順に5問ずつ実行した。各回の前に8トークンのウォームアップを行い、スロット消去後の5問を集計した。初回はONの起動ログを繰り返し必須とするランナーの判定で最終OFFに進まなかったため、判定を修正し、完走した再計測4回を本集計に使った。D4 ONでIQ2_S・IQ3_XXSとも1・2トークン版を確認。全20応答EOS、応答中のホストスワップアウト0、サーバー終了コード0。

| 指標 | D4 OFF | D4 ON |
| --- | ---: | ---: |
| 新規プリフィル tok/s（合算） | 51.96 | 53.38 |
| 生成 tok/s（合算） | 60.48 | 61.84 |
| 各回の生成 tok/s | 59.78 / 61.21 | 61.34 / 62.33 |
| MTP採用 / 提案 | 1,321 / 2,096 | 1,395 / 2,170 |

合算速度は総トークン数÷総処理時間。OFFの最終回の第4問は375トークンをプリフィルし、ONの各回では134トークンだった。履歴とキャッシュ再利用量が変わるため、総処理時間は施策単体の比較に使わない。新規プリフィルトークン数が揃う第1〜3問で、OFFの最終回は54.88 tok/s、ONは55.15 / 54.98 tok/sだった。生成の差は小さく、MTP採用率も63.02% / 64.29%と異なる。この4回で明瞭な速度低下は観測されなかった。

通常の非同期広幅プリフィルでは、`use_wide_prefill` がtrueの場合にD4用の狭幅マーカーは設定されない。通常設定の速度計測として狭幅の値は使わない。[完走した4回と生ログ](/home/t-saka/rocm-iq-mmvq-d4-adopted-speed-20261127-repeat/session-batch-01)
