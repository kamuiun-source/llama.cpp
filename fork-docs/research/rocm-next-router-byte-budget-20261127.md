# 固定3幅の次層Expert先読みバイト予算

## 変更範囲

RTX 4070 TiとMI50を使う単一バンク、固定MTP 3幅、直接tuple DMA、動的常駐の次層先読みが対象。現行の予測候補を従来順で最大8枠に並べ、既存の後発行キューで残り時間内に収まる全Expert tupleだけを発行する。予測Router、正規Router、既存の候補順位とスコア設定、仮置き枠・RAM原本の寿命管理は従来どおり。コピーは同時に最大2件。先の層で未使用のH2Dが残れば、その完了を既存イベントの照会で確認するまで次の発行を遅らせる。正規Router IDを取得した層の未発行分は既存の優先処理で取り消す。後発行コールバックを設置できない場合、予算ONではその層の先読みを休止する。

MoE-Infinityの計算窓と転送帯域からバイト量を求める方式を、この単一ストリーム用に適用した。[調査と出典](rocm-handoff-expert-transfer-20261127.md#expert転送)

## 計算窓と帯域

Expertを投入した直後から次層の正規Router IDを取得するまでのホスト経過時間を対象層ごとに記録する。各観測の40%を使い、直近の値を1/4、従来値を3/4で更新する。サンプルがない層の予算は0。計算窓がCPU側の待ちや低速回で膨らみ過ぎないよう240 µsを上限にし、発行時点までに過ぎた時間を引く。前の発行分のイベント完了を確認してから次のバッチを発行するため、そこで費やした時間も差し引かれる。ホスト時刻による近似であり、GPUの実稼働時間はrocprofで確認する。

240 µsは、固定3幅D4採用後のトレースのMI50活動11.108 ms/検証を48層で割った約231 µsを丸めた上限。同じトレースの273グラフを対象に、投入後コールバックの開始から次層の重みコールバックの開始まで12,831組を対応させた。正規Router読出しは後者の中で行われる。観測の第1四分位・中央値・第3四分位は514 / 536 / 568 µs。MI50活動の層平均はこの中央値の約43%に当たるため、割引率を40%に固定した。先読みストリーム4の主な転送長1,983,744 Bと2,201,472 Bで、rocprof上のDMA帯域の第1四分位は約13.67 GB/sと13.73 GB/s。発行・競合の余裕を見て12,000 B/µsを使う。払出上限は時間に比例し、最大2,880,000 B。保存トレースのモデルのtupleは1,511,424〜2,663,424 Bのため、予算ONのこの条件では1層あたり0件または1件になる。容量の小さいtupleは、残り時間と8枠に収まる範囲で2件ずつ発行できる。帯域の実行時再推定は今回の範囲外。[校正元の固定3幅トレース](../rocm/latest-performance.md#d4採用後の統合版で検証を詳細計測)

## 比較手順

同じCUDA/HIP増分ビルドと固定3幅の採用設定を使う。起動時に `LLAMA_EXPERT_HIP_NEXT_ROUTER_PREFETCH=1`、`LLAMA_EXPERT_HIP_NEXT_ROUTER_BUDGET_TELEMETRY=1`、`LLAMA_EXPERT_OUTPUT_MODE_FILE` を指定する。既存のヒット待ち・後発行を有効にする。起動時の `LLAMA_EXPERT_HIP_NEXT_ROUTER_BYTE_BUDGET=1` は初期値をONにする。既定はOFF。

サーバーがアイドルのとき、モードファイルへ `NEXT_ROUTER_BYTE_BUDGET=off` または `NEXT_ROUTER_BYTE_BUDGET=on` を入れる。既存の `NEXT_ROUTER_PREFETCH` や `HIP_PREFILL` の行は必要に応じて同じファイルに維持する。次のリクエストから変更し、モデル再ロードや自動キャッシュ消去は発生しない。既存の採用設定からモードファイルを作成する場合は、同一ディレクトリの一時ファイルから `mv` で置き換える。

OFFで固定3幅の短いウォームアップを実行して各層の窓を学習させ、`off → on → off` を同一プロセスで比較する。各回で同じウォームアップとスロット消去を行い、同じ入力・生成上限で[固定5問](dialogue-benchmark-prompts.md)を実行する。生ログと終了コードはGit管理外へ保存する。速度比較ではトレースとプロファイラーを外す。別のトレース付き比較で生成ID、MTP提案・採用数、正規RouterのExpert ID、重み転送の件数と時刻を確認する。先読みで供給するIDと通常H2DのIDは配分が変わり得る。

`packed expert HIP next Router byte budget` の各モード累計は、モード切り替え時と終了時に出る。OFF計測はテレメトリを有効にして採る。境界の差分から `h2d_tuples/bytes`、`ready_hits/ready_hit_bytes`、`late_hits/late_hit_bytes`、`demand_tuples/bytes`、`demand_sync_us` を比較する。ready/lateは正規Routerを読み取った時点でH2Dイベントが完了していたかを、実際にD2Dで使用したExpertについて数える。`demand_sync_us` は同期経路でのホスト待ちで、H2D・依存D2Dの両方を含み得る。非同期需要経路を併用する場合は既存の検証トレースも確認する。`candidates` は従来順で並べた転送候補数、`blocked/blocked_bytes` は予算で候補から外れた量、`blocked_selected` はそのうち正規Routerが選んだ件数。`observed_layers` と `window_sample_us` は窓のサンプル件数と、40%への換算と上限適用後の時間合計。`unarmed_layers` は後発行の安全条件が揃わなかった層数。

出力と正規RouterのIDが一致し、予算ONで発行量が変化することを確認する。ready hitと需要待ちに加え、通常実行の検証時間・生成速度およびスワップを比較して採否を決める。GPUでの動作と速度差は未確認。

CUDA/ROCm開発イメージをGPUなしで使い、`llama-moe-cache.cpp` と `llama-context.cpp` のC++17構文を確認した。ホスト確認は、初回0と期限切れ、tupleサイズによる払出の変化、層別推定値とON/OFF累計の3ケース。モードファイルはスタブでOFF→ON→OFF、他2項目との併用、重複行の拒否を確認した。
